Verify a ticket

A Stamp ticket is a promise you can check. The engine is pure - data in, ticket out - so the same inputs always give the same ticket, byte for byte, and the same hash.

What the hash covers

hash = sha256(canonical JSON of the ticket without hash and narration). Canonical means keys sorted and no floats: every price and amount is a decimal string. The narration is a template written after the verdict, so it's left out. The ticket also carries inputsHash (the exact Binance data it saw) and policyHash.

Three ways to check

  1. In the browser: press verify on any ticket, or paste a hash on proof. Stamp fetches the stored inputs, recomputes, and says MATCH or NO MATCH.
  2. Over HTTP: GET /v1/tickets/:hash, then send its input and ticket to POST /v1/verify. matches: true means the ticket is genuine and unchanged.
  3. Offline: clone the repo and run the replay. It recomputes every recorded ticket with no network and exits 1 if one hash drifts.
npm ci && npm run replay
# 621 tickets recomputed · all hashes match

What's recorded

Test cases in fixtures/golden/ (one per rule), and real captures of Binance's responses in fixtures/replay/: Friday 25 Sep (pre-market, cash hours, the 20:00 close pause, after-hours), Saturday 26 and Sunday 27 Sep (tokens trading while the stock market is shut), and Monday 28 Sep (pre-market and cash hours). A GitHub Action snapshots 20 tickers every ten minutes into the snapshots branch; that is where Stamp's recorded close comes from.

What a match doesn't prove

A match proves the verdict follows from the recorded inputs under the recorded policy. It doesn't prove Binance's data was right - that is why Stamp blocks on data that disagrees with itself instead of choosing.
